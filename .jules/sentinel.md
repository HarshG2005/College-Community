## 2024-10-24 - Defensive Input Coercion and Unintended Mongoose Query Behaviors

**Vulnerability:** A Type DoS and NoSQL injection risk was identified across multiple Express routes (e.g., `auth.js`, `placements.js`) where user-supplied inputs (`req.body.email`, `req.query.type`) were directly chained into string methods (`.toLowerCase()`) or regex initializers (`new RegExp()`) without explicit type validation or casting. While attempting to fix this by coercing the input to a string, a secondary vulnerability was almost introduced: setting the fallback value to `undefined` (e.g., `email !== undefined ? String(email) : undefined`).

**Learning:** When a variable is coerced and the fallback is `undefined`, and that variable is passed directly into a Mongoose `findOne` query (e.g., `User.findOne({ email: undefined })`), Mongoose deliberately strips the `undefined` field from the query object. This causes the query to effectively become `User.findOne({})`, which subsequently returns the *first* document in the entire collection (frequently an admin account). In the context of an authentication route, this converts a Denial of Service vulnerability into a Critical Authentication Bypass / Account Takeover risk.

**Prevention:** When mitigating Type DoS and NoSQL object injection by explicitly coercing optional string inputs, always fall back to a safe, falsy default string (e.g., `email ? String(email) : ''`) rather than `undefined`. Alternatively, implement strict type checking (e.g., `typeof email === 'string'`) and throw a 400 Bad Request error if the structure is unexpected, ensuring the application fails securely.
